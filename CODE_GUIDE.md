# How to explain the code

## 1. The whole project in one sentence

The browser sends HTTP requests to Express; Express checks the user and input, uses Mongoose to read/write MongoDB, and returns JSON that browser JavaScript turns into the page.

```text
public/index.html + style.css + app.js
                  ↓ fetch('/api/...')
                server.js
                  ↓
       helpers.js / models.js / reports.js
                  ↓
                MongoDB
```

There is no React, frontend build, ORM service layer, or dependency-injection framework. The few separate files have one understandable responsibility each.

## 2. Recommended explanation order

1. `package.json`: packages and commands.
2. `.env.example`: settings without real secrets.
3. `models.js`: document fields, constraints and relationships.
4. `helpers.js`: short reusable validation/security functions.
5. `server.js`: middleware and routes, grouped by feature.
6. `public/index.html`: fixed page shell.
7. `public/style.css`: layout and responsive visual rules.
8. `public/app.js`: request helper, navigation, page builders and form handlers.
9. `reports.js`: calculations and role-specific report tables.
10. `demo-users.js`: three fixed demo emails/roles and their public demo password.
11. `seed.js` / `demo.js`: presentation setup; demo startup re-hashes/restores only the three fixed accounts, leaving other MongoDB records intact.

`package-lock.json` is generated by npm, and `types.d.ts` plus lint/format configuration are development tooling rather than application logic.

## 4. MongoDB and Mongoose: `models.js`

- A **collection** contains documents; it plays a similar role to a table.
- `Schema` describes fields and validation. `mongoose.model(...)` provides collection operations.
- `required`, `min`, `max`, `enum`, and `validate` reject invalid documents.
- `timestamps: true` adds `createdAt` and `updatedAt`.
- `ObjectId` identifies a document. `ref` tells Mongoose which model it references.
- `populate('venue')` replaces a venue ID with the related venue document for display.
- `lean()` returns ordinary objects when document save methods are unnecessary.
- `select: false` keeps hashes and email tokens out of ordinary responses.
- Unique indexes prevent duplicates **in the database**, even under concurrent requests. The event title index uses case-insensitive collation.

Explain each schema field using its name and the PDF checklist. The six main entities are User, Event, Registration, Venue, Feedback and Notification. Suggestion supports platform feedback; Activity supports signup/login reporting.

## 5. Validation and security: `helpers.js`

### `fail(condition, message, status)`

If the invalid condition is true, it throws an error with an HTTP status. Routes remain easy to read: validate first, then modify data. Express's final error handler turns the error into JSON.

### Password hashing

`hashPassword` generates a random salt, derives a 64-byte hash with `scrypt`, and stores `salt:hash`. `checkPassword` validates that format, repeats the calculation using the stored salt, and compares equal-length buffers with `timingSafeEqual`. The original password is not stored.

### `accountInput` and `eventInput`

These convert raw values, enforce the PDF's rules, check database-dependent rules such as venue capacity/bookings, and return only permitted fields. They do not copy arbitrary request fields into a document.

### Other helpers

- `list`: split comma-separated interests/amenities into a clean array.
- `source`: clean a promotion source label.
- `owns`: admin or the event's organizer can manage it.
- `sentiment`: count whole words in positive/negative lists; use the sign of the score.
- `notify`: create one notification.
- `notifyAttendees`: notify registered, waitlisted and checked-in users.
- `sendReminders`: find approved events starting within 24 hours; notify each eligible student once.

The few `@type` comments describe populated documents or transaction results to the JavaScript checker. They do not change runtime behavior or introduce TypeScript into the app.

## 6. The server: `server.js`

### Imports and access-control helpers

Packages are loaded first. `publicUser` exposes only small safe account fields. `requireLogin` reads the session's user ID, confirms that the account is active, and attaches `req.user`. `requireRole` checks the permitted roles. `managedEvent` also checks event ownership; `visibleEvent` allows public approved events and authorized private/history views.

### `createApp`

1. Create the Express application.
2. Require a session secret and parse JSON.
3. Configure a server-side session store and HTTP-only cookie.
4. Add security headers and reject unexpected mutation origins.
5. Serve the frontend and validated public images, not the project root.
6. Rate-limit authentication requests outside the test environment.
7. Register feature routes.
8. Finish with not-found and error handlers.

`req.params` contains URL IDs; `req.query` contains filters; `req.body` contains form JSON. `res.json` returns JSON; `res.status(201)` means a record was created. Typical errors are 400 invalid input, 401 not logged in, 403 forbidden, 404 missing, and 409 conflicting/duplicate record.

### Route groups

- **Auth:** validate signup, hash password and token, deliver/preview confirmation, verify once, log in with a fresh session, log out.
- **Profile/users:** read/update profile and preferences; deactivate safely; let admins activate users and verify organizers.
- **Venues:** add/edit/read/archive; protect future bookings and event capacities.
- **Events:** filter/read; create/edit in a transaction; reset edits to pending; approve/reject; cancel/archive; evaluate completed execution.
- **Registrations:** reserve/waitlist, cancel/promote, show history/tickets/attendees, mark attendance, connect opted-in students.
- **Feedback:** require completed checked-in attendance; validate all six ratings; create/edit one review per attendee; respond/delete with ownership checks.
- **Notifications:** history, mark read, archive, clear, organizer messages.
- **Suggestions/uploads:** store submissions/progress; validate/compress images; restrict screenshot access.
- **Reports:** call `buildReport` for the authenticated role.

### Why transactions are necessary

When two students request the last seat, a simple read-then-save could let both in. `$expr` compares allocated seats with capacity **inside the database update**. `$inc` changes the count atomically. A transaction makes the event update, registration record and related notification succeed or fail together.

`mongoose.connection.transaction(async dbSession => ...)` starts this operation; queries using `.session(dbSession)` or `{ session: dbSession }` belong to it. Mongoose retries transient conflicts. Waitlist promotion selects the earliest request and maintains the seat count. Venue writes similarly serialize overlapping bookings, using `bookingVersion` as a shared write point.

### Startup

`startServer` connects to MongoDB, verifies transaction support, initializes indexes, creates the first admin if needed, creates the app, listens on the web port, and schedules reminder checks. Environment variables are loaded by `dotenv`, not hardcoded into production code.

## 7. The frontend

### `public/index.html`

The sidebar, top bar, application container, toast and modal are permanent. `app.js` changes their contents. The browser directly loads the CSS and JavaScript.

### `public/style.css`

Explain it in groups: color variables/base elements → sidebar/header → hero/event cards → forms/tables → modals/toasts → responsive media queries. Flexbox aligns elements; CSS Grid lays out cards/forms; media queries adapt to smaller screens.

### `public/app.js`

- State at the top stores the current user, configuration, events, venues and report.
- `$` finds a page element; `esc` escapes user-controlled text before HTML insertion.
- `date`, `tag`, `field`, `select`, and `heading` create consistent display/form pieces.
- `api` sends `fetch` requests and throws server error messages. File uploads use `FormData`; normal requests use JSON.
- `run` displays errors for button actions. `submit` prevents normal form navigation, reads values and disables buttons while saving.
- `renderNavigation` chooses links by role. `route` reads the URL hash and calls the correct page function.
- Page functions read data then render ordinary HTML template strings. Nearby form handlers save data, show a toast and refresh that view.
- Reports build tables; export helpers download Blob files. CSV export protects spreadsheet formula cells.
- Hash navigation is used instead of a frontend routing library.

Inline `onclick`/`onsubmit` handlers keep the connection between a button/form and its function visible for explanation. Browser checks improve UX, but backend validation and permissions remain authoritative.

## 8. Reporting: `reports.js`

Explain `average`, `percent`, `groups`, and `themes` first. Then `buildReport`:

1. Select events/registrations/feedback appropriate to the role.
2. Build an event-ID lookup for related records.
3. For students, return their history/feedback and score future recommendations.
4. For organizers/admins, calculate event rows, attendance, feedback and promotion tables.
5. For admins only, add user, organizer, venue, activity and platform-suggestion reports.

Attendance percentage is checked-in students divided by allocated registrations. Waitlisted/cancelled requests do not count as allocated seats. Averages and percentages explicitly handle empty arrays/zero denominators.

## 9. Trace one complete request line by line

Use **student RSVP** as your main explanation example:

1. Event detail's button calls `registerEvent(id)`.
2. `registerEvent` calls `api('/events/.../register', 'POST', ...)`.
3. `api` sends JSON with `fetch` and the browser's session cookie.
4. Express runs `requireRole('student')`, which includes `requireLogin`.
5. The route starts a transaction and verifies the approved future event and organizer.
6. It rejects a duplicate active registration.
7. It atomically attempts to increment the seat count.
8. It creates/reuses a registration as registered or waitlisted, with a random QR token.
9. It updates source statistics and creates an RSVP notification.
10. The transaction commits, and `res.status(201).json(registration)` returns the result.
11. `api` parses JSON; `registerEvent` shows the result and refreshes the details.

Then repeat that approach for event creation, email confirmation, waitlist cancellation, check-in, feedback and report generation. Follow the actual statements in each function rather than memorizing framework jargon.

## 10. Packages: why each exists

| Package                             | Purpose                                               |
| ----------------------------------- | ----------------------------------------------------- |
| Express                             | HTTP routes and static frontend                       |
| Mongoose                            | MongoDB models, validation, queries, transactions     |
| dotenv                              | Private local configuration                           |
| express-session / connect-mongo     | Login sessions stored in MongoDB                      |
| express-rate-limit                  | Limit repeated authentication attempts                |
| validator                           | Email format validation                               |
| multer / sharp                      | Receive, verify, resize and compress images           |
| qrcode                              | QR ticket images                                      |
| marked / sanitize-html              | Markdown rendering without unsafe markup              |
| nodemailer                          | Optional email confirmation delivery                  |
| mongodb-memory-server               | Real local/disposable MongoDB for demo/tests          |
| supertest                           | Test HTTP routes without a browser                    |
| ESLint / TypeScript / type packages | Development checks on JavaScript                      |
| Prettier                            | Readable formatting; not needed by the running server |

Node's built-in `crypto`, `fs`, `path` and test runner need no extra runtime package. All dependencies are justified by a PDF workflow, security requirement, local-demo convenience or verification task.
